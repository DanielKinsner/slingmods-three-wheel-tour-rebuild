# Revision04 failure: source modifier miter explosion

The lead correctly rejected the runtime candidate. The exported body had a roughly 79 m longitudinal extent although its wheel pivots remained unchanged. My earlier check asserted pivot/UV contracts and recorded body bounds, but failed to **assert** those body bounds. That was an inadequate preflight.

`vehicle_p03a_diagnose.py` opened the preserved failed Blender source and measured every evaluated object. The sole out-of-scale source object was `windshield_cowl_bridge`, with Blender Y minimum -76.7297 m and Z minimum -9.31137 m. Its newly connected section doubled back at the center, and the Solidify modifier's Even Thickness mode generated an unbounded miter. This was not caused by the console pocket Boolean. In a controlled ablation on the same source, disabling only `use_even_offset` reduced the bridge to its expected bounds (recorded in `revision04-failed/offending-source.json`).

Repair: order the cowl's cross-section points monotonically front-to-back; use bounded normal-offset thickness instead of Even Thickness for these thin shells. Added an evaluated-source whole-vehicle size assertion before saving/exporting. A subsequent actual-GLB world-bounds check exposed another distinct issue: arbitrary rotated origins inherited from the first merged component made transformed accessor bounding boxes too loose (~35 mm below ground). Each exported batch now bakes into its declared binding's local space and has identity local transform. This keeps GLB/renderer Box3 bounds tight without moving any actual geometry or protected pivot.

The repaired actual GLB bounds match the accepted P01 bounds: X [-0.9945, 1.0015], Y [0, 1.312732], Z [-2.1200, 1.6790] metres. The validator now asserts the whole exported world-bounds size within 1% of P01 in addition to all protected transforms, UVs and baseline Git blobs. Runtime visual reinspection is still required; successful structural checks do not approve materials or appearance.
